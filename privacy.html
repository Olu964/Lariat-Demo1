Privacy Policy

Lariat turns Texas bill summaries into clear, business-ready signals. This policy explains what information we collect, why we collect it, and the choices you have.

✦ Effective September 7, 2026

1. What this policy covers

This policy applies to the Lariat site, including the landing page, the Bill feed, Find your legislator, Calendar, Pricing, and the optional email subscription flow. Browsing does not require an account, payment, or login. Billing, customer accounts, and recurring bill-alert delivery are not active features in the current code. The frontend can be served as static files by Vercel, but the subscription and legislator features work only when a separately configured Lariat backend is reachable; a static deployment alone does not create that backend.

How the bill feed is produced. The feed is populated by an automated pipeline that fetches public Texas bill records from the Open States API and attempts to retrieve official Texas Legislature bill text over HTTPS. When usable official text is available, OpenRouter AI drafts a structured summary from that text and public record metadata. When usable official text cannot be obtained, the pipeline may publish a shorter, explicitly labeled metadata-only summary; it does not claim that metadata-only text is a substitute for bill text. The scheduled job runs through GitHub Actions, which can fetch, summarize, and commit updated public records. These pipeline steps are separate from visitor use of the site and do not intentionally include visitor personal information in AI requests.

Who operates this service. Lariat is the service name used by this prototype. It is currently presented as a demo rather than a finalized paid product or a statement of legal entity status. For privacy questions, requests, or concerns, use the contact address in section 11.

2. Information we collect

The current application collects or processes the following information:

  • Email address - entered when you request a subscription verification email and retained with a confirmed subscription. In the browser, the subscription badge record also contains the entered email address, industry, and verification timestamp.
  • Industry preference - the industry selected for a subscription.
  • Verification code and private access code - the verification code is checked by the backend and stored only as a salted scrypt hash while pending; it expires after the configured lifetime (10 minutes by default) and is never stored in plaintext. The private access code is checked and is not stored.
  • Browser storage - the display name entered when you first open the site, bill notes, light/dark theme preference, selected demo plan, the first-visit demo notice flag, the local subscription badge state, and the local access-code lockout timer are stored in localStorage on the device. The signed unsubscribe token is not stored in browser storage.
  • Location lookup information - when you use Find your legislator, the address or ZIP code you submit is sent to the configured Lariat backend. The backend sends the address to the U.S. Census Bureau for geocoding, confirms the result is in Texas, and sends the resulting coordinates to Open States to identify the current Texas state senator and representative. A successful lookup is cached privately for up to 24 hours under a normalized input key together with the returned public profile and available vote-history result; failed and no-match lookups are not cached. The submitted address is not placed in the public page URL or sent directly to browser-side third-party scripts. Use a ZIP code if you do not want to submit a full street address, understanding that ZIP results can be approximate.
  • Network and operational information - the backend reads the connecting IP address for rate limiting and access-code lockout. It keeps rate-limit data in process memory and stores an HMAC-derived key plus failure-count and lockout timestamps for the access-code lockout; the raw IP address is not written to the subscription JSON file. The server logs the HTTP method and path for API requests, while a hosting provider, reverse proxy, firewall, or server process may keep additional access logs. In local console mode, the server also prints the recipient email, verification code, and unsubscribe link needed for testing.

When you first open pages that use the greeting feature, we ask for a display name to personalize the greeting. The name is stored only in your browser's localStorage, is never sent to our backend, and is not used for any other purpose. The frontend may also store whether the homepage demo notice has been shown and, after incorrect subscription access-code attempts, a local countdown used to update the lockout message; the backend enforces the lockout separately. We do not ask for payment information or precise location. Do not put confidential information into bill notes: localStorage is user-controlled and is not an encrypted workspace. If you use local console mode, treat the terminal output as sensitive because it can contain an email address, a verification code, and an unsubscribe link.

3. How we use your information

  • Your email address and industry are used to request and, when Brevo is configured, deliver the verification and welcome emails, and to retain your confirmed email-list subscription. Without Brevo credentials, local console mode prints the verification code and unsubscribe link to the server terminal instead of sending email. The current backend does not contain a scheduled recurring bill-alert delivery job, so no recurring bill alerts are sent by this demo. The current implementation sends a verification email and, after confirmation, a welcome email containing an unsubscribe link when email delivery is configured.
  • The verification code confirms control of the email address; it is used for no other purpose and is not stored in plaintext.
  • The IP address is used transiently for abuse prevention and rate limiting.
  • A submitted address or ZIP code is used to perform the legislator lookup, cache a successful result for 24 hours, and return the matched delegation. Open States may return public legislator profile and vote-record data; Lariat does not infer a vote that is absent from the source.
  • Bill notes, theme preference, selected demo plan, and subscription badge state remain in browser storage. The selected demo plan controls the number of industry subscriptions the demo UI permits; it is not payment or account authorization.

We do not sell your information or use it for advertising or profiling.

4. Where your information lives

In your browser. The feed stores the display name entered on first visit, bill notes, theme preference, selected demo plan, local subscription badge state, the first-visit demo notice flag, and the local access-code lockout timer in localStorage. The badge state includes the email address, industry, and verification timestamp returned after confirmation. The signed unsubscribe token is delivered by email and is intentionally not stored in browser storage.

On the backend host. In local development, the backend stores subscription records, pending-code hashes, lockout metadata, and legislator lookup cache files under server/data/, outside the public site directory. Pending verification codes are stored only as salted scrypt hashes with a 10-minute expiry. Failed access-code lockout records contain an HMAC-derived network key, a failure count, and timestamps; raw IP addresses are not written to the file. These files are suitable for local testing, not production. A Vercel static deployment does not provide durable writable storage for them; production must move subscriptions, cache data, rate limits, and retention controls to managed persistent storage and a protected backend.

With our email provider. To deliver verification and welcome emails, the backend sends the recipient email address, sender information, message content, selected industry, and the signed unsubscribe URL in the relevant welcome message to Brevo. Brevo's own privacy policy governs its processing. No payment information is collected by the current subscription flow.

With lookup and legislative-data providers. The backend sends an entered address or ZIP code to the U.S. Census Bureau's geocoding services and sends only resulting coordinates to Open States to identify current Texas state legislators. To show recent voting history, it requests public bill and vote records from Open States; the Lariat server matches those public records to the returned legislator profile and sends the result to your browser. Lariat does not request or display legislator contact information. Review the Census Bureau privacy policy and Open States' terms and privacy information.

With hosting and infrastructure providers. A public deployment may expose request metadata, such as IP address, timestamps, user agent, requested URL, function logs, and security events, to Vercel, a separate backend host, a reverse proxy, or other infrastructure providers according to their policies. GitHub may process repository and workflow metadata when GitHub Actions runs the bill-data pipeline. These providers should be configured with the minimum access, retention, and logging necessary for the deployment.

5. Third-party services

  • Brevo - delivers verification and welcome emails when Brevo email delivery is configured and a subscription flow is completed. In local console mode, the server prints testing values instead. See their privacy policy.
  • Google Fonts - loads the site's typography. Google may log standard request information when the fonts load; see Google's privacy policy.
  • Texas Legislature - the feed links out to capitol.texas.gov so you can verify bill status with the official source. That site is outside our control.
  • Open States - supplies the Texas bill records, public legislator records, and available individual vote records used by the site. See their Terms of Use & Privacy Policy.
  • U.S. Census Bureau - geocodes a submitted Texas address or ZIP code and confirms whether the resulting coordinate is in Texas. See the Census Bureau privacy policy.
  • OpenRouter AI - generates bill summaries from official legislative text and record metadata. No visitor personal information is included in these requests. See OpenRouter's privacy information for provider details.
  • GitHub Actions - runs the scheduled fetch-and-summarize job. It has access only to public bill records and repository automation secrets; it is not intended to receive visitor personal information. See GitHub's privacy statement.
  • Vercel - may host the static frontend and process deployment, CDN, request, and function metadata when the site is deployed through Vercel. Vercel does not automatically provide the persistent subscription store or the long-running Node backend used in local development. See Vercel's privacy policy.

6. Cookies and tracking

The current frontend does not set application cookies and does not include analytics, advertising trackers, or fingerprinting code. It uses localStorage for the display name entered on first visit, bill notes, theme, selected demo plan, local subscription badge state, the first-visit demo notice flag, and the local access-code lockout timer; unsubscribe tokens are not stored there. The Free, Professional, and Business choices are demo-only browser state; billing, payment processing, customer accounts, and server-side plan authorization are not active. When the subscription flow is used, the browser sends the entered email, industry, access code, and later verification code to the configured Lariat backend. When Find your legislator is used, the browser sends the entered address or ZIP code to the configured backend; the browser does not call Census or Open States directly and does not store that lookup in localStorage. If the Vercel frontend has no configured backend, those features display an unavailable/configuration response rather than silently storing the submitted data. The browser does not send the display name, bill notes, theme preference, demo notice flag, lockout timer, or plan selection to the backend. Vercel, the backend host, Brevo, Census, Open States, GitHub, and other linked third parties may maintain their own technical logs.

7. How long we keep information

  • Verification codes expire after the configured lifetime (10 minutes by default), are stored only as salted scrypt hashes, and are removed when verified or when expired records are pruned during a later subscription request or verification.
  • Access-code lockout records are removed after the 24-hour lockout window or after the associated failure window expires. They contain an HMAC-derived network key rather than the raw IP address.
  • Subscriptions remain in the configured backend store until unsubscribed or deleted by the operator. The local prototype does not implement an automatic retention period. Signed unsubscribe links expire after the configured token lifetime, 90 days by default; expiration does not itself delete the subscription record.
  • Browser data - the display name entered on first visit, bill notes, theme preference, selected demo plan, subscription badge state, first-visit demo notice flag, and local access-code lockout timer remain until removed by the site, changed or cleared through the relevant demo controls, or cleared in browser settings. Unsubscribe tokens are delivered by email and are not stored in browser storage. The reset-subscriptions control removes the local subscription badge state but does not clear the selected demo plan, display name, notes, demo-notice flag, lockout timer, delete the backend subscription, or bypass a server-enforced access-code lockout.
  • Legislator lookup cache - successful address or ZIP lookups are retained by the configured backend for up to 24 hours to avoid repeating external geocoding and legislative-data requests, then become eligible to be replaced or removed by normal cache maintenance. The current prototype does not expose a self-service cache deletion control; contact the operator at the address below for a deletion request. A production deployment must use a shared, access-controlled cache or database rather than relying on local filesystem state.
  • Infrastructure logs - retention is controlled by the hosting provider, reverse proxy, and operator's logging settings. The intended operational target is 365 days where the provider supports it, but the current local prototype does not implement automatic log retention or deletion.

8. Your choices and rights

  • Stop receiving update emails: the Bill feed's Unsubscribe button only explains that the email link must be used; it does not remove the backend record. Open the unsubscribe link in a Lariat welcome email and explicitly confirm the action. This removes the matching record from the backend when the token is valid and current.
  • Clear browser state: use Reset demo subscriptions on the Bill feed, or clear this site's data in your browser settings. Reset clears the browser subscription badge and local subscription state, but it does not clear the selected demo plan, delete the backend subscription, or bypass a server-enforced access-code lockout.
  • Access or correct: in the local prototype, the operator can inspect the backend data file and users can inspect their browser storage. For a public deployment, contact the operator at the address below to request access, correction, or deletion.

Unsubscribe requests require the signed token issued after email verification. The current demo sends verification and welcome emails but does not send recurring bill alerts. Address and ZIP lookup requests are used only to perform the configured lookup and short-lived cache described above. For privacy questions or requests, contact us using the details in section 11. If the product later adds analytics, cookies, recurring alerts, accounts, payments, durable user profiles, or additional data uses, this policy must be updated before those features are enabled.

9. Children's privacy

Lariat is not directed at children under 13, and we do not knowingly collect information from them. If you believe a child has shared information with us, contact us and we will remove it.

10. Security

The current backend uses salted scrypt hashes for pending verification codes, short expirations, limited verification attempts, three failed access-code attempts followed by a 24-hour lockout, request limits, strict input handling, signed expiring unsubscribe tokens, server-side email delivery, and restricted static-file serving. Brevo, Census, and Open States requests use HTTPS. The development server binds to 127.0.0.1 by default and keeps subscription and lookup data outside the public site directory. A public Vercel deployment must use HTTPS, a separately deployed protected backend or Vercel Functions, secret management, persistent storage, shared rate limiting, backups, monitoring, and the full security checklist; hosting the static files on Vercel alone does not provide those application controls.

SSL / HTTPS Security

What HTTPS does

HTTPS uses TLS to encrypt traffic between a browser and the HTTPS endpoint, helping protect data in transit from interception or alteration. It does not make information secure after it reaches the browser, server, email provider, hosting provider, logs, or backups.

Current deployment behavior

In local development, Lariat intentionally runs on http://127.0.0.1:3000. In production configuration, the Node server requires an HTTPS public URL, redirects requests that the trusted reverse proxy reports as plain HTTP, and sends an HSTS header. The deployed static site also declares HSTS and security headers through its hosting configuration.

What production still requires

  • A trusted reverse proxy or managed host must terminate TLS and maintain a valid certificate.
  • The proxy must pass a correct X-Forwarded-Proto value, protect the origin, and apply appropriate rate limits.
  • Secrets, subscription data, logs, backups, and infrastructure access must be protected separately from transport encryption.
  • Users should check the browser's secure-connection and certificate indicators before entering an email address.

Scope

Lariat does not operate or warrant the TLS configuration of every host, proxy, browser, email provider, or linked third-party website. Confirm the actual deployed connection before collecting real subscriber information. This statement is informational, not a security certification.
